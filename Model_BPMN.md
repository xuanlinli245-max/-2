# Model BPMN — место модели в процессе скрининга

## 1. Схема процесса

```mermaid
flowchart LR
    A([Пациент на приёме]) --> B[Сбор 11 клинических признаков]
    B --> C{Данные проходят валидацию?}
    C -- Нет --> C1[Сообщить об ошибке<br/>оценка не выполняется]
    C -- Да --> D[Pipeline:<br/>очистка, импутация,<br/>кодирование, масштабирование]
    D --> E[[Voting ensemble:<br/>LogReg + RandomForest + HGB]]
    E --> F[P(заболевание)]
    F --> G{P >= 0.107?}
    G -- Да --> H[Высокий риск:<br/>осмотр врача в течение 24 ч]
    G -- Нет --> I[Ниже порога:<br/>плановое наблюдение]
    H --> J[Врач принимает решение]
    I --> J
    J --> K[Запись в аудит:<br/>версия модели, порог, вход]
    K --> L([Мониторинг и обратная связь])
```

## 2. Краткое описание для задания

### Какую задачу решает модель

Модель оценивает вероятность сердечно-сосудистого заболевания по 11 рутинным клиническим
признакам и помогает приоритизировать пациентов для врачебного осмотра. Она **не ставит диагноз**
и **не назначает лечение**.

### Почему здесь целесообразно использовать ML

Связь между возрастом, давлением, холестерином, типом боли, ЭКГ, пульсом и риском заболевания
нелинейна и многомерна. Простое правило вида «если давление выше X» давало бы много пропусков
и ложных срабатываний. ML находит комбинацию признаков и обобщает её на новых пациентов;
порог затем настраивается под клиническую политику.

### Какие данные поступают на вход

11 признаков: возраст, пол, тип боли, давление, холестерин, сахар натощак, ЭКГ, максимальный пульс,
стенокардия при нагрузке, `Oldpeak`, наклон ST. Данные проходят проверку схемы и диапазонов;
при ошибке оценка не выполняется.

### Как результат используется дальше

Врач видит вероятность, порог и группу риска:

- **high** → осмотр в течение 24 часов;
- **lower** → плановое наблюдение.

Решение и версия модели фиксируются в аудите. Врач может переопределить вывод с обязательной
причиной. Результат не пишется в медицинскую карту автоматически.

## 3. Роли

| Роль | Ответственность |
|---|---|
| Медсестра / ассистент | ввод признаков, проверка полноты |
| Врач | интерпретация, решение, подпись |
| ML-инженер | версия модели, мониторинг, retraining |
| Владелец продукта | порог, KPI, приоритеты |
| Комплаенс / этика | DPIA, регуляторные требования |

## 4. Guardrails

- Модель не заменяет врача и не ставит диагноз.
- Ошибка валидации — жёсткий стоп, а не «тихая» импутация.
- High-risk сопровождается дисклеймером «требует врачебного review».
- Каждая оценка логируется с версией модели и порогом.
- Человек может переопределить решение; причина фиксируется.
- Перед пилотом обязательны fairness-аудит и DPIA.

## 5. Метрики процесса

- доля пациентов, охваченных скринингом;
- время до врачебного review для high-risk;
- recall на размеченной выборке;
- доля ошибок ввода;
- p95 latency API.
